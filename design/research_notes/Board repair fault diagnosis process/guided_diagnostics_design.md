# Guided diagnostic software and structured troubleshooting procedures: tools, formalisms and design lessons (as of November 2026)

Reading notes for the report writer:

- Each finding ends with its source. `[read]` means the page or PDF text was read directly during this research. `[excerpt]` means only a search-result excerpt or an automated page summary was seen, so the wording should be checked before it is quoted.
- Constraint tags used throughout: **[simple]** fits a single-user local app with a multimeter and no data, **[needs golden board]** needs a known-good board or reference values, **[needs dataset]** needs a large fault or case database, **[needs expert model]** needs an expert to enter causes, probabilities and costs by hand.
- Formulas are written in plain text so they can be implemented directly.

## 1. What existing software guides electronics or board repair?

### Takeaway

Board repair software today is reference material, not guidance: boardview tools show where a net goes and (at best) what a healthy board reads on it, wikis list causes per symptom in likelihood order, and automated testers compare a board with a golden reference. No tool found leads a technician step by step through a board-level diagnosis while tracking suspects from the board's own netlist, which is the gap the Investigate feature would fill.

### Cited Findings

#### Boardview tools

- FlexBV shows reference values per net taken from OpenBoardData: hovering a pin shows "the expected diode mode value of the net and the normal running voltage", pins can display diode, voltage and resistance values, and a Measure panel shows the "Diode, resistance and voltage OBData values" of the selected net. **[needs golden board]** (Source: [FlexBV manual](https://pldaniels.com/flexbv5/manual/flexbv-manual.html) `[excerpt of fetched page]`)
- FlexBV has an "OBData Coverage" layer that highlights "all pins/nets with OBData values", so the user sees where reference data is missing. (Source: [FlexBV manual](https://pldaniels.com/flexbv5/manual/flexbv-manual.html) `[excerpt of fetched page]`)
- FlexBV can read live multimeter readings from a text file (`mmdata.txt`), average a sliding window of samples, colour stable versus unstable readings, and queue them for submission to OpenBoardData (`.obdq` pending, `.obdlog` archive, `.obdlocal` local-only). (Source: [FlexBV manual](https://pldaniels.com/flexbv5/manual/flexbv-manual.html) `[excerpt of fetched page]`)
- FlexBV has three net-tracing aids: Netweb (a trace from the selected pad to every other pad on the net), Constellation (fewer branches, for dense power rails) and Mycelium, which expands the selected net through likely low-ohm links (fuses, inductors, shunts, low-value resistors) up to three levels deep. This is a shipped example of treating series elements as joins between nets. (Source: [FlexBV manual](https://pldaniels.com/flexbv5/manual/flexbv-manual.html) `[excerpt of fetched page]`)
- FlexBV's `.obdata` file "contains repair guides, component values and diode/volt measurements", and after a download the info panel shows "if there are any repair solutions added". The manual describes no dedicated known-fault database and no step-by-step guidance. It also keeps per-board annotations in a SQLite file and a jobs database whose contents the manual does not describe. (Source: [FlexBV manual](https://pldaniels.com/flexbv5/manual/flexbv-manual.html) `[excerpt of fetched page]`)
- OpenBoardData is a community database of board repair data "including network volt, diode, and resistance measurements", stored as plain text, with no limit on brands or board types, contributed through FlexBV. **[needs golden board]** (Source: [OpenBoardData readme listing](https://awesome.ecosyste.ms/projects/github.com%2Finflex%2Fopenboarddata) `[excerpt]`)
- OpenBoardView (open source) opens `.brd` files and offers part and net search, a net list, a part list, per-board annotations and a "common net pin halo". Its README mentions no diode or voltage data and no troubleshooting workflow. (Source: [OpenBoardView README](https://github.com/OpenBoardView/OpenBoardView) `[excerpt of fetched page]`)
- ZXW and Wuxinji are described as the two most used paid "bitmap" tools for phone boards (a point-to-point map of pads and traces alongside schematics). Diode-value coverage varies by model: an iFixit forum answer says of one model that it "does not have diode readings". Licensing reports conflict (dongle plus yearly licence versus cloud account login in a 2026 vendor blog). (Sources: [diyfixtool 2026 overview](https://www.diyfixtool.com/blogs/news/2026-free-schematic-tools-for-mobile-phone-and-iphone-repair), [Elektroda Q&A](https://www.elektroda.com/qa,mobile-phone-schematics-download-sources.html), [iFixit Answers thread](https://ts.ifixit.com/Answers/View/651566/Does+anyone+have+any+good+iPhone+5s+diode+mode+readings+please) `[excerpt]`, all vendor or forum sources)
- JC Drawing (JCID "intelligent drawing") lists 1:1 bitmaps, schematics, a "resistance preview", "repair cases sharing" and a personal cloud database of voltage and resistance-to-ground readings. The companion JCID D11 detector measures voltage, resistance, diode values and shorts and sends them to the software over Bluetooth. **[needs golden board] [needs dataset]** (Sources: [JCID product page](https://www.jcprogrammer.com/product/jc-drawing-card-schematic-diagram-inode-bitmap-for-iphone-android-mobile-phone-jcid), [JCID D11 listing](https://www.diyfixtool.com/products/jcid-d11-multifunctional-digital-detector-with-jc-intelligent-maintenance-drawings) `[excerpt]`, vendor marketing)
- REFOX bitmap (free, promoted by REWA) advertises a "Diode/Voltage Value Reference". (Source: [REWA article](https://rewa.tech/free-boardview-schematics-bitmap-for-logic-board-repair) `[excerpt]`, vendor promotion)

#### Repair wikis

- An iFixit Problem Page is titled "[Device Name] [Problem]" and has three parts: an introduction (the problem, background, first steps), a solutions section and a conclusion. Each level-2 heading is one cause, and "the heading should be written as a cause rather than a solution" ("The battery is dead", not "Replace the battery"). Causes are ordered with "more probable (or more-easily-eliminated) causes generally coming first". The conclusion is "a place to suggest next steps if nothing among the causes and solutions has worked". **[simple]** (Source: [iFixit Problem Page guidance](https://www.ifixit.com/Info/Problem_Page) `[excerpt of fetched page]`)
- iFixit's education material repeats the rule: one user-observed symptom per page, all possible causes as headers, ranked from most to least likely, solutions in short paragraphs, links to repair guides. (Sources: [iFixit EDU milestone overview](https://edu.ifixit.com/milestone-1-overview), [iFixit EDU common mistakes](https://edu.ifixit.com/common-student-mistakes) `[excerpt]`)
- Repair Wiki defines a repair guide as "documentation of single problem and its solution(s)", with template fields for affected parts, equipment needed, type and difficulty, a title that is what a person "would naturally type into Google", and steps split into bullet and numbered lists. Diagnostic explanations go on separate explanatory pages. (Sources: [Repair Wiki repair guide help](https://repair.wiki/w/RepairWiki:RepairGuideHelp), [Repair Wiki guidelines](https://repair.wiki/w/RepairWiki:Guidelines) `[excerpt]`, the site returned 403 to a direct fetch)
- The RetroTechCollection wiki builds its troubleshooting guides from symptom tables with three columns (Symptom, Probable cause, Action), "list the most likely cause first", and requires every action to be doable: "name the test point and the expected value from the schematic. 'Measure +5 V at pin 8 of the 6502' is useful; 'check the power supply' is not". Typical sections start with preliminary and power-up checks and a voltage reference table. **[simple]** (Source: [RetroTechCollection, Writing a repair guide](https://retrotechwiki.com/Help:Writing_a_repair_guide) `[read]`)

#### Automated test systems and golden references

- Analog signature analysis (Huntron Tracker) is a power-off test: a current-limited AC sine wave is applied across two points and current is plotted against voltage. "All analog signatures are a composite of one or more of the four basic component signatures which are: resistance, capacitance, inductance and semi-conductance", and a short circuit shows as a vertical line. (Source: [Huntron, Fundamentals of Signature Analysis](https://smtnet.com/library/files/upload/ASA%20white%20paper.pdf) `[read]`)
- "In most cases, analog signature analysis is used for comparison troubleshooting. This means that the signatures of a good printed circuit assembly (PCA) are compared to those of a suspect PCA. Signature differences can indicate a potential problem." Channel A holds the good board and channel B the suspect. **[needs golden board]** (Source: [Huntron, Fundamentals of Signature Analysis](https://smtnet.com/library/files/upload/ASA%20white%20paper.pdf) `[read]`)
- Huntron also documents ways to work without a good board: compare similar pins on the same IC, compare bus lines against each other ("Address lines should exhibit the same signatures as well as data lines"), and "Begin testing complex boards by probing its connectors". It adds that "if a bussed component has more than one bad signature besides a faulty bus line then that component is likely to be the actual failure". **[simple]** as a heuristic (Source: [Huntron, Fundamentals of Signature Analysis](https://smtnet.com/library/files/upload/ASA%20white%20paper.pdf) `[read]`)
- Huntron Workstation software can store several serialized signature sets to compare against, and the 2800 series offers over 100 combinations of voltage, source resistance and frequency, so reference and test readings must use the same settings. (Source: [Metromatics on the Huntron Tracker 2800S](https://metromatics.com.au/product/analog-signature-analysis-huntron-tracker/) `[excerpt]`)
- ABI's SYSTEM 8 and BoardMaster use a "TestFlow" to produce "customized sequential test methods" including V-I testing and live board comparison. A training board ships with a TestFlow file that "guides the operator through a series of tests", ABI says low-level operators only follow on-screen instructions, and a manual exercise says the best use of the digital V-I test is to compare a good and a bad board. This is the closest commercial analogue of a guided bench procedure, but the sequence is fixed and reference-based. **[needs golden board]** (Sources: [ABI product brochure](https://www.abielectronics.co.uk/PDF/ABI%20Product%20Brochure.pdf), [ABI SYSTEM 8 manual](https://manualshive.com/en/manual/abi/system-8/451443?page=2), [Test and Measurement Tips on BoardMaster](https://www.testandmeasurementtips.com/board-tester-from-saelig-verifies-component-pcb-module-performance/) `[excerpt]`)
- In-circuit and flying-probe test compare each measurement with programmed two-sided limits. Early flying probers used "learn-and-compare": a master is learned from a board, written as "golden" if no defects are found, and later boards are compared with it. Keysight notes that measurement validity depends on isolation and guarding. **[needs golden board]** (Sources: [Keysight ICT overview](https://literature.cdn.keysight.com/litweb/pdf/5992-2186EN.pdf?id=2842871), [PCB007 Magazine](https://iconnect007.uberflip.com/i/819981/94), [EPP article by GenRad](https://epp.industrie.de/allgemein/important-part-of-an-answer/) `[excerpt]`)

#### Open-source and recent tools

- Wrench Board (2026) is "an AI-powered diagnostic workbench for board-level electronics repair": it takes a schematic PDF and a boardview file, builds a device-specific knowledge pack, and a language-model agent highlights pins, traces nets and simulates faults. The agent "is not allowed to invent a component reference". Sessions can be replayed. The article does not say it takes meter readings as structured input, and iFixit's Kyle Wiens notes that schematic and boardview files "are still very rare". (Source: [Fight to Repair interview](https://fighttorepair.substack.com/p/how-ai-is-set-to-transform-electronics) `[excerpt of fetched page]`)
- RepairLedger is described as an open-source repair specification covering diagnosis, repair, verification and maintenance that treats each repair decision as an evidence problem. BugBuster is open hardware that lets AI models measure and control real hardware. (Sources: [GitLab electronics-repair topic](https://gitlab.com/explore/projects/topics/electronics-repair), [Hackster on BugBuster](https://www.hackster.io/news/bugbuster-gives-ai-the-tools-to-debug-physical-hardware-f4fd22236ce4) `[excerpt]`)
- Academic board-level work exists on adaptive diagnosis with decision trees built from earlier diagnosis sessions (Bolchini and Cassano, Politecnico di Milano). **[needs dataset]** (Source: [DFT 2015 paper](https://re.public.polimi.it/retrieve/handle/11311/985725/111437/DFT2015.pdf) `[excerpt]`)

### Inferences

- The products split into three families: (a) reference viewers (boardview plus expected values), (b) symptom-to-cause documents (iFixit, Repair Wiki, service wikis), (c) reference comparators (Huntron, ABI, ICT). None of them reasons over the netlist to choose the next measurement. The app already holds what (a) holds plus a confidence per connection, so the new value is the reasoning layer.
- The most transferable ideas at no data cost: iFixit's "heading is a cause, not a fix" and "most probable or most easily eliminated first"; RetroTech's "name the test point and the expected value"; FlexBV's coverage layer (show where no expected value exists) and Mycelium (follow low-ohm series parts); Huntron's "compare similar pins or channels on the same board" when no golden board exists.
- Expected values are the weak point for a one-off board with no schematic. The app can only state expectations that follow from physics and the netlist (a rail is not 0 ohm to ground, 5 V appears on the 5 V net, two pins on one net read continuity), plus datasheet values, and must label everything else as "no reference".

### Gaps

- Borneo Schematics and Phoneboard: no reliable source found on their diagnostic features. One search returned only an untrustworthy page for Borneo and nothing for Phoneboard.
- ZXW, Wuxinji and JCID features are sourced only from vendor pages, reseller blogs and forums. Whether their "repair case" libraries are structured (symptom, measurement, fix) could not be verified.
- The internal format of an OpenBoardData entry and of FlexBV repair guides was not found.
- No tolerance-band rules for golden-board comparison (how many boards to learn from, how to set limits) were found in ICT or Huntron sources.
- Whether Wrench Board is open source and whether it records measurements was not confirmed.

## 2. How do other industries structure guided diagnostics for technicians?

### Takeaway

Every industry surveyed uses one of two shapes. The older and most common is a static, authored tree per fault code or symptom (aviation FIM and S1000D, automotive test plans, service-manual tables), always wrapped in the same envelope: entry by symptom or code, prerequisites and safety, confirm the fault exists, branch on observations, fix, then confirm the repair. The newer shape is a dynamic engine that recomputes the best next step from a cause model after each answer (Dezide and the HP SACSO work with Bayesian networks, TEAMS with dependency matrices, Class V IETMs).

### Cited Findings

#### Aviation and military

- An S1000D fault data module (the public "bike" sample, schema `fault.xsd`) contains: a fault code and fault description ("NYCJD04", "Tire does not function correctly"), references to other data modules, preliminary requirements (required conditions, support equipment, consumables, spares, safety conditions), the isolation procedure, and "Requirements after job completion". Metadata includes applicability and a skill level ("Basic"). (Source: [S1000D bike sample data module](https://www.docuneering.com/s1000d/demo/pdf/DMC-S1000DBIKE-AAA-DA0-10-20-00AA-400A-A_007-00_EN-US.pdf) `[read]`)
- The isolation steps in that sample are: step 1, an action (check the pressure with the tire pressure gauge) plus a question ("What is the tire pressure reading?") with three answer ranges, each naming the next step (more than 2700 hPa goes to step 2, between 100 hPa and 2700 hPa to step 3, less than 100 hPa to step 4); a later step asks a yes/no question ("Is there damage to the tire?", yes goes to step 5, no to step 6); leaf steps are a repair action that refers to another procedure and end with "Go to requirements after job completion". So the structure is a decision tree whose nodes are action plus question, whose edges are answer choices (not only yes/no, numeric ranges too), and whose leaves are fixes. **[simple]** (Source: [S1000D bike sample data module](https://www.docuneering.com/s1000d/demo/pdf/DMC-S1000DBIKE-AAA-DA0-10-20-00AA-400A-A_007-00_EN-US.pdf) `[read]`)
- Other public S1000D samples show an "observed fault" module with a fault code, description and isolation test, and a component-level module with numbered fault entries, yes/no questions, action steps and an end element. (Sources: [S1000D lighting sample](https://www.docuneering.com/s1000d/demo/pdf/DMC-S1000DLIGHTING-AAA-D00-00-00-00AA-413A-A_007-00_EN-US.pdf), [CMP42 sample](https://www.docuneering.com/s1000d/printing/ata-spec-1000br-data-module-to-pdf/DMC-CMP42-A-23-10-10-06A-420A-A_001-00_sx-US.pdf) `[excerpt]`)
- A Boeing 737 FIM task is "a tree structure in the form of text paragraphs". Most tasks start with an Initial Evaluation whose purpose is to "verify that the fault condition still exists before you start the fault isolation procedure"; if the fault cannot be confirmed, the task says it was intermittent and the airline's intermittent-fault policy applies. After each corrective action come repair confirmation steps, and if the fault persists the technician returns to the step after the one that sent them to confirmation. Each fault has an eight-digit fault code that indexes the task. (Source: [AviationHunt, Boeing 737 fault isolation standard practices](https://aviationhunt.com/?p=6844) `[excerpt of fetched page]`, a third-party summary, not Boeing's document)
- The same page says both "Do the steps of the task in the specified order" and "It is not a requirement to do the steps in the FIM task in the order shown", with the caution that "Some FIM tasks have important steps that have an effect on other steps later in the task", and that Boeing recommends doing the repair confirmation after any corrective action, even one not in the task. The source is internally inconsistent on step order. (Source: [AviationHunt](https://aviationhunt.com/?p=6844) `[excerpt of fetched page]`)
- IETMs are classed I to V: page images, scrolling documents, linearly structured, hierarchically structured, and Class V "integrated database" manuals that integrate with equipment diagnostics. One patent describes a Class V IETM providing "Dynamic Diagnostics" by interrogating the system under test from XML-encoded "Diagnostic Fault Flows". MIL-PRF-87269A (1995) superseded MIL-D-87269 (1992) for the database. (Sources: [Wikipedia, IETM](https://en.wikipedia.org/wiki/Interactive_electronic_technical_manual), [DTIC IETM guide](https://apps.dtic.mil/sti/tr/pdf/ADA376398.pdf), [US patent 7,823,062](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/7823062) `[excerpt]`)
- A DTIC paper on dynamic fault isolation argues static fault trees are limited to a single-fault assumption, and describes a run-time "Diagnostician" whose "algorithms and knowledge bases (matrix) operate to isolate fault without troubleshooting sequences and without hard-code diagnostic logic", using a fault propagation connectivity matrix. (Source: [DTIC ADA455068](https://apps.dtic.mil/sti/tr/pdf/ADA455068.pdf) `[excerpt]`)
- The US Navy six-step troubleshooting procedure (NEETS Module 19): "1. Symptom recognition", "2. Symptom elaboration. Obtaining a more detailed description of the trouble symptom", "3. Listing probable faulty functions... where could the trouble logically be located?", "4. Localizing the faulty function", "5. Localizing trouble to the circuit. You will do extensive testing in this step", "6. Failure analysis. This step is multipart. Here you determine which part is faulty, repair/replace the part, determine what caused the failure, return the equipment to its proper operating status, and record the necessary information in a recordkeeping book". Hints: observe "any and all faults", check "with your eyes and nose", and "Analyze the cause of the failure for a possible underlying problem". **[simple]** (Sources: [NEETS Module 19, six-step procedure](https://electriciantraining.tpub.com/14191/css/Six-Step-Troubleshooting-Procedure-144.htm), [NEETS Module 19, steps 5 and 6](https://electriciantraining.tpub.com/14191/css/Classes-Of-Overhaul-Work-145.htm) `[read]`)

#### Automotive

- VW ODIS Guided Fault Finding builds "test plans": per-control-module plans loaded from stored fault codes, with a tab to view DTCs and a diagnosis protocol created for each session. An older VAS 5051 tutorial says a system test plan is built from stored fault entries, the customer complaint, or both, and the user can build their own plan. (Sources: [ODIS Service manual copy](https://www.scribd.com/document/493942193/ODIS-Service-Manual), [VAS tutorial](https://www.scribd.com/document/307427884/Vas-Tutorial) `[excerpt]`)
- Volkswagen's own service bulletin lists content defects of that approach: fault codes that are "active/static but no test created in current test plans for the fault code" (several entries), a starter test whose step states the voltage "is OK" although "Starter did not turn", and a test step that names control module J518 while "the wiring diagram calls out J965". Technicians are told to "Send feedback once test has ended". (Source: [VW ODIS service bulletin VOS-22-16 via NHTSA](https://static.nhtsa.gov/odi/tsbs/2022/MC-10209102-0001.pdf) `[read]`)
- Bosch ESI[tronic] SIS troubleshooting instructions are reached from a fault code and are described by Bosch as "step-by-step testing including OE values and real-time comparison with VCI multimeter measurements". **[needs golden board]** in the sense of manufacturer nominal values (Sources: [Bosch ESI fact sheet](https://www.boschaftermarket.com/xrm/media/images/equipment/esitronic_software/xx_pdf_1/tds_fact_sheet_esi_en_77391.pdf), [PMM on SIS instructions](https://pmmonline.co.uk/technical/how-to-improve-your-kts-diagnostics-capabilities-3/) `[excerpt]`)
- Bosch "Experience-based repair (EBR), Known Fixes" is case-based: "500.000 real-life use cases/vehicle combinations", free-text search over "error codes, symptoms, and even components, as well as faults without error codes stored", a "Common structure of the repair instructions", and a feedback function so that "the required solutions are frequently listed at the top". **[needs dataset]** (Source: [Bosch EBR fact sheet, 2018](https://www.boschaftermarket.com/xrm/media/images/equipment/esitronic_software/xx_pdf_1/tds_fact_sheet_ebr_en.pdf) `[read]`)

#### Field-service decision tools

- Dezide (Aalborg, since 2001) states that its engine "weighs failure probabilities, repair costs, and everything the technician has answered, then calculates the best next step", and that it "computes the best next question or action at every step", with guides usable online, offline and for self-service. A software listing describes its guides as built from "causes, probabilities, actions, questions, cost and time". **[needs expert model]** (Sources: [Dezide home page](https://www.dezide.com/) `[read]`, [GetApp listing](https://www.getapp.ca/software/101063/dezide) `[excerpt]`)
- Dezide descends from the HP and Aalborg University SACSO project ("Systems for Automated Customer Support Operations"); its BATS tool (Bayesian Automated Troubleshooting System) "is available from Dezide". BATS was built so "that any user, however, inexperienced, should be able to repair the failed equipment on his own", and "The BATS system consists of about 40 separate BN models, each representing a specific failure-mode. Some models are quite small, but the largest contains about 80 actions and 40 questions", built by a team of six to seven experts with an authoring tool that needs no Bayesian network knowledge. (Source: [Langseth and Jensen 2003, Decision theoretic troubleshooting of coherent systems](https://www.fs.isy.liu.se/Edu/Courses/DocDiagnos/CourseMaterial/troubleshooting_coherent_systems.pdf) `[read]` via an archived copy)
- The SACSO data structure is one naive Bayes model per error condition: a single cause variable whose states are the causes, with every action and question as a child, so "all observations (actions and questions) are independent given the causes". Steps are of three kinds: solution actions (can fix and end the session), information-gathering actions (a temporary change such as swapping a cartridge, treated as questions) and questions (information only). (Sources: [Skaanning 2000, A Knowledge Acquisition Tool for Bayesian-Network Troubleshooters](https://arxiv.org/pdf/1301.3893) `[read]`, [US patent 6,535,865](https://patents.google.com/patent/US6535865) `[excerpt of fetched page]`)
- The HP patent explains why other structures were rejected: decision trees are static, every allowed sequence must be encoded by hand, and the result is "longer troubleshooting sequences with lower probability of actually diagnosing the problem"; case-based systems would need a very large case base (at least 21,000 configurations estimated). (Source: [US patent 6,535,865](https://patents.google.com/patent/US6535865) `[excerpt of fetched page]`)
- Zingtree deploys authored decision trees with "Back" and "Restart" buttons that can be disabled per workflow or per node. ServiceNow's decision trees let agents return to earlier nodes and jump to a prior node from a "View my responses" tab. Yonyx is a similar authored decision-tree platform with a map view beside the interactive view. **[simple]** to imitate (Sources: [Zingtree help, Back and Restart buttons](https://help.zingtree.com/hc/en-us/articles/5003243194651), [ServiceNow decision tree nodes](https://www.servicenow.com/docs/r/5M2H7PAkXUuakbtz~5Kfeg/GtEU3GitckLHvuEVyncsNg), [Knowmax on Yonyx](https://knowmax.ai/blog/yonyx-alternatives/) `[excerpt]`)

#### Medical devices and other service manuals

- Service manuals use symptom tables. Midmark's troubleshooting chart has four columns: Symptom, Probable Cause, Check, Correction. Mindray lists possible causes per failure and a "Correction Action". A Siemens ultrasound guide states that "if more than one possible cause is listed, the cause on top is the one that is most probable (or most easy to check)". Defibrillator manuals map error codes to a description and a fix. **[simple]** (Sources: [Midmark 625 troubleshooting chart](https://technicallibrary.midmark.com/Tables/SR/625-SR-00034.htm), [Mindray T1 service manual](https://www.manualslib.com/manual/1265611/Mindray-T1.html?page=57), [Siemens SONOLINE troubleshooting guide](https://www.scribd.com/document/802674324/Trbl-Guide), [Army medical maintenance course](https://armymedical.tpub.com/MD0362/Locate-the-Cause-of-the-Malfunction-Example-1-DefibrillatorMonitor-74.htm) `[excerpt]`)

#### Data structure by approach

| Approach                | Data structure                                                                                        | Who uses it                                          | Needs                                        |
| ----------------------- | ----------------------------------------------------------------------------------------------------- | ---------------------------------------------------- | -------------------------------------------- |
| Symptom table           | Rows of symptom, probable cause (ordered), check, correction                                          | Service manuals, iFixit, RetroTech wiki              | An author. **[simple]**                      |
| Fault isolation tree    | Nodes of action plus question, edges per answer, leaves of fix, wrapped in prerequisites and close-up | S1000D, Boeing FIM, ODIS test plans, Zingtree, Yonyx | An author per symptom. **[simple]**          |
| Case base               | Past cases indexed by symptom and code, ranked by feedback                                            | Bosch EBR, phone repair case libraries               | **[needs dataset]**                          |
| Golden reference        | Expected value or signature per node, with tolerance                                                  | Huntron, ABI, ICT, OpenBoardData                     | **[needs golden board]**                     |
| Dependency (D) matrix   | Binary matrix of fault versus test, plus priors and test costs                                        | TEAMS (Qualtech), Class V IETM "Diagnostician"       | A dependency model. Derivable from a netlist |
| Bayesian troubleshooter | Causes with probabilities, actions and questions with costs and conditional probabilities             | Dezide, HP SACSO, Microsoft troubleshooters          | **[needs expert model]**                     |
| Model-based diagnosis   | Component models plus connections, conflicts and candidates computed at run time                      | GDE (research), see section 3                        | Behaviour models per part                    |

### Inferences

- The envelope common to S1000D, the FIM and NEETS maps directly onto a session: (1) symptom and its elaboration, (2) prerequisites and safety, (3) confirm the fault still exists, (4) isolation steps, (5) corrective action, (6) repair confirmation, (7) record and root cause. Steps 3 and 6 are the ones hobby repair usually skips.
- S1000D shows that a "question" should be modelled as an action plus a question with a small set of labelled answer ranges, each mapped to an outcome. For a measured value, the technician enters the number and the tool classifies it into the ranges, which keeps the raw observation.
- For one board with no fault history, the realistic choices are a hand-authored tree per symptom, or a small dependency model derived from the netlist with rough priors. The Bayesian tools show the second can still be simple when restricted to a single-cause variable with independent tests.
- The VW bulletin shows the characteristic failure of authored test plans: missing branches and steps that contradict the documentation. A tool for one evolving board model should therefore generate steps from the model where possible and always offer a "this step is wrong or not applicable" exit.

### Gaps

- No primary VW or Bosch document describing how a test plan chooses or orders its steps was found. The ODIS description rests on manual copies and an old tutorial.
- The official S1000D specification text (element names such as the isolation step and answer elements, and the fault information codes) was not read; only sample data modules were.
- ATA iSpec 2200 FIM structure was not sourced from ATA. The Boeing description is third-party and contradicts itself on step order.
- Yonyx and Zingtree guidance on "not sure" answers and session history was not found. Dezide's product internals are sourced from its marketing page plus the academic papers it descends from.
- No WHO or regulator document on medical service-manual troubleshooting format was found.

## 3. What does the research literature say about the best next test to run?

### Takeaway

Three families of result agree on one implementable rule: keep a probability per suspect, and at each step pick the action with the best ratio of expected benefit to cost, recomputing after every answer. For a check that can find the fault, the benefit is the probability it is there (rank by p/C). For a pure information test, the benefit is expected information gain or expected reduction in remaining cost (rank by gain per cost; half-split is the equal-probability, equal-cost special case). All of them are one-step (myopic) heuristics that are optimal only under a single-fault, independent-cost assumption.

### Cited Findings

#### Decision-theoretic troubleshooting (Heckerman, Breese, Rommelse; Breese and Heckerman)

- Assumptions: one problem-defining variable, the device is faulty at the start, and "Single fault: Exactly one component is abnormal", with p_i the probability that repairing component c_i repairs the device, so the p_i sum to 1. Each component is observable (can be tested, cost C_i^o, then repaired at cost C_i^r if faulty) or unobservable (can only be repaired or replaced). (Source: [Breese and Heckerman 1996, Decision-Theoretic Troubleshooting: A Framework for Repair and Experiment](https://arxiv.org/pdf/1302.3563) `[read]`)
- Expected cost of repair when observing and repairing in the order c_1 ... c_n: `ECR = sum over i of (1 - sum of p_j for j < i) * C_i^o + p_i * C_i^r`. (Source: [Breese and Heckerman 1996](https://arxiv.org/pdf/1302.3563) `[read]`)
- The ordering rule: "By reversing the order of the any two steps in the repair sequence, one can show that the minimum expected cost sequence is obtained by ordering the components according to a decreasing probability to cost ratio", that is `p_1/C_1^o >= p_2/C_2^o >= ... >= p_n/C_n^o`. An unobservable component is included by setting its observation cost to its repair cost and its repair cost to zero. **[simple]** (Source: [Breese and Heckerman 1996](https://arxiv.org/pdf/1302.3563) `[read]`)
- General (non-base) observations are handled by one-step lookahead: `ECO(I, o) = C_o + sum over outcomes k of Pr(o = k | I) * ECR(I and o = k)`. The procedure: compute ECR for the current information, compute ECO for every available observation, and "recommend that repair, observation, or configuration-observation that has the lowest expected cost", then update probabilities and repeat. (Source: [Breese and Heckerman 1996](https://arxiv.org/pdf/1302.3563) `[read]`)
- A third step type is the configuration change (change a setting, observe, change back), costed as the change cost plus the same expectation. Their printing example: print locally, with probability 0.42 of output and an expected cost of 7.07 minutes after it, 13.83 minutes otherwise. (Source: [Breese and Heckerman 1996](https://arxiv.org/pdf/1302.3563) `[read]`)
- Unknown causes are lumped into a single "all other" fault "that can be repaired at a fixed cost with a service call". The method "will run (albeit approximately) for a device with multiple faults". It was applied to printing, car start-up, copier feeders and gas turbines and shipped in the Windows 95 support resource kit. (Source: [Breese and Heckerman 1996](https://arxiv.org/pdf/1302.3563) `[read]`)
- The original result is attributed to Heckerman, Breese and Rommelse (1995, Communications of the ACM) and the 1994 technical report MSR-TR-94-07, where for two components c_1 is repaired first when p_1/C_1 > p_2/C_2. (Sources: [Microsoft Research, Decision-Theoretic Troubleshooting](https://www.microsoft.com/en-us/research/publication/decision-theoretic-troubleshooting/), [Troubleshooting Under Uncertainty](https://www.microsoft.com/en-us/research/publication/troubleshooting-under-uncertainty/) `[excerpt]`)

#### SACSO, BATS and Dezide refinements

- Efficiency of an action A given evidence e: `ef(A | e) = P(A solves the problem | e) / C_A`. In an optimal sequence with independent costs, each action's efficiency is at least that of its successor, which characterises some sub-optimal sequences but does not prove optimality. A worked example shows the greedy sequence with ECR 1.58 against an optimum of 1.47, and the remedy offered is "to recalculate the efficiencies each time new evidence comes in". (Source: [Langseth and Jensen 2003](https://www.fs.isy.liu.se/Edu/Courses/DocDiagnos/CourseMaterial/troubleshooting_coherent_systems.pdf) `[read]` via an archived copy)
- When to ask a question Q: `VOI(Q) = ECR(S') - sum over answers q of P(Q = q) * ECR(S | Q = q)`, where S' is the best strategy without Q, and "The system should pose the question if VOI(Q) > C_Q". The practical version is myopic: only re-sequence actions by efficiency for each answer, which over-rates questions somewhat. (Source: [Langseth and Jensen 2003](https://www.fs.isy.liu.se/Edu/Courses/DocDiagnos/CourseMaterial/troubleshooting_coherent_systems.pdf) `[read]` via an archived copy)
- Greedy efficiency ordering is optimal under a single fault, perfect repair actions, independent actions and independent costs; SACSO's actions are imperfect and dependent, yet comparisons with optimal sequences found "only minor differences". (Source: [SACSO methodology paper record, Jensen et al. 2001](https://portal.mardi4nfdi.de/wiki/Item:Q2758715) `[excerpt]`)
- Cost is a weighted sum of factors: time in minutes, risk of breaking something else, money, and "insult" (a step too basic for the user), `C = a*T + b*R + c*M + d*I`, with risk, money and insult on a five-level scale. (Source: [Skaanning 2000](https://arxiv.org/pdf/1301.3893) `[read]`)
- Operator error is modelled explicitly: `P(A solves | cause) = P(A solves | cause, done correctly, requisites available) * P(done correctly) * P(requisites available)`. The "inaccuracy factor" expresses "how much the user's result is trusted". (Source: [Skaanning 2000](https://arxiv.org/pdf/1301.3893) `[read]`)
- In the HP patent's example weights, risk is multiplied so that "a 0 minute step with very high risk is equal to a 72 minute step with very low risk". The user can decline a step "if he is unable to perform it, or simply doesn't want to at the moment"; declined steps go to a deferred pool and are offered again once untried steps run out. If the troubleshooter fails, the log of steps and the final cause probabilities are handed to a human agent. (Source: [US patent 6,535,865](https://patents.google.com/patent/US6535865) `[excerpt of fetched page]`, equations were partly illegible in the extract)

#### Test sequencing (Pattipati and Alexandridis) and D-matrices (TEAMS)

- The test sequencing problem is "the five-tuple (S, P, T, C, D)": S the failure sources plus a dummy fault-free state, P their probabilities under a single-fault assumption, T the tests, C the test costs "measured in terms of time, manpower requirements, or other economic factors", and a binary test matrix B = [b_ij] whose "rows and columns ... correspond to failure sources and tests". "The problem is to design a testing strategy that unambiguously isolates the failure sources with minimum expected testing cost", represented as an AND/OR tree whose OR nodes are suspect sets and AND nodes are tests. "The test matrix can be computed by the reachability analysis algorithms." (Source: [Pattipati et al. 1997, Multiple Fault Isolation in Redundant Systems, NASA final report](https://ntrs.nasa.gov/api/citations/19980096374/downloads/19980096374.pdf) `[read]`)
- The original paper (Pattipati and Alexandridis 1990, IEEE Trans. SMC 20(4), 872 to 887) formulates the problem as optimal binary AND/OR decision tree construction, which is NP-complete, and guides heuristic search with lower bounds on cost-to-go derived from Huffman coding and entropy. Earlier "information" and "separation" heuristics can be far from optimal in some cases. (Sources: [bibliographic record](https://bvbvf1.bib-bvb.de/vufind/PrimoRecord/cdi_ieee_primary_65446), [summary record](https://www.bohrium.com/paper-details/application-of-heuristic-search-and-information-theory-to-sequential-fault-diagnosis/812460977139220482-13723) `[excerpt]`)
- A D-matrix is "an n x m matrix M such that for every entry m_ij, a value of 1 indicates that d_i is a parent of t_j" (diagnosis i can make test j fail). Diagnoses with identical rows form an ambiguity group: "no tests exist capable of differentiating the classes". (Source: [Wahl and Sheppard 2010, Extracting Decision Trees from Diagnostic Bayesian Networks to Guide Test Selection](https://www.cs.montana.edu/sheppard/pubs/phm-2010.pdf) `[read]`)
- Test selection by information gain: `gain(e) = I(current) - E(e)`, where E(e) is the expected entropy of the partitions the test would create, and the test with the largest gain is chosen. A cost-weighted variant multiplies the expected remaining entropy by cost(e) and weights each class by a utility, so cheap tests are preferred at equal information. Weighting the D-matrix rows by prior probability gave compact, accurate trees in their comparison. (Source: [Wahl and Sheppard 2010](https://www.cs.montana.edu/sheppard/pubs/phm-2010.pdf) `[read]`)
- TEAMS-RT infers component health from test outcomes: tests are pass, fail or unknown, and components are classified as "Good, Bad, Suspect and Unknown". A caution from the NASA work: a "FAIL" outcome "does not mean that one or more of the implicated components are faulty because the test outcome may have been a false alarm". Pure dependency reasoning yields large suspect sets and carries no probabilities, which is why some convert the D-matrix to a Bayesian network. (Sources: [NASA paper on TEAMS-RT](https://ntrs.nasa.gov/api/citations/20140008893/downloads/20140008893.pdf), [PHM Society paper](https://www.papers.phmsociety.org/index.php/phmconf/article/download/2392/1358), [US patent 5,544,308](https://patents.google.com/patent/US5544308) `[excerpt]`)
- For multiple faults, Pattipati's group distinguishes "hidden faults" and "masking false failures" and repeats a single-fault strategy in a test-and-repair cycle, removing repaired modules from the ambiguity group and re-running ("Sure strategies"). (Source: [NASA final report 1997](https://ntrs.nasa.gov/api/citations/19980096374/downloads/19980096374.pdf) `[read]`)

#### Model-based diagnosis (de Kleer and Williams, GDE)

- "A conflict is a set of components which cannot all be functioning correctly" (the set of components a contradicted prediction depended on). A candidate is "a set of failed components, where any components not mentioned are guaranteed to be working", and "each set representing a candidate must have a nonempty intersection with every conflict". Minimal candidates are updated incrementally: when a new conflict arrives, any candidate that does not intersect it is replaced by copies each extended with one component of the conflict, and non-minimal results are dropped. (Source: [de Kleer and Williams 1987, Diagnosing Multiple Faults](https://www.fs.isy.liu.se/Edu/Courses/DocDiagnos/CourseMaterial/deKleer_Williams_1987.pdf) `[read]` via an archived OCR copy)
- GDE needs only "the a priori probabilities of individual component failure". Assuming components fail independently, each candidate gets a prior, and posteriors shift by Bayes' rule as measurements arrive. (Sources: [de Kleer and Williams 1987](https://www.fs.isy.liu.se/Edu/Courses/DocDiagnos/CourseMaterial/deKleer_Williams_1987.pdf) `[read]`, [de Kleer 2009, IJCAI](https://ijcai.org/proceedings/2009/127) `[excerpt]`)
- Next measurement: "the best measurement is the one which minimizes the expected entropy of candidate probabilities resulting from the measurement", with `H = - sum of p_i * log p_i` and `He(x) = sum over values v_k of p(x = v_k) * H(x = v_k)`. This is "a one-step lookahead strategy"; full lookahead "can be implemented as a classic decision tree analysis, but the computational cost of this analysis is prohibitive". All measurements are assumed to cost the same. (Source: [de Kleer and Williams 1987](https://www.fs.isy.liu.se/Edu/Courses/DocDiagnos/CourseMaterial/deKleer_Williams_1987.pdf) `[read]`)
- Candidates that predict nothing for a quantity are "uncommitted" and spread evenly over the m possible values: `p(x = v_k) = p(S_k) + p(U)/m`, where S_k is the set of candidates predicting v_k and U the uncommitted set. The paper states this deliberately does not assume a faulty part must misbehave now, "because a component may appear to be functioning correctly, but actually be faulted producing incorrect outputs for a different set of inputs". (Source: [de Kleer and Williams 1987](https://www.fs.isy.liu.se/Edu/Courses/DocDiagnos/CourseMaterial/deKleer_Williams_1987.pdf) `[read]`)
- "The expected entropy can be calculated from the current candidate probability distribution", so "there is no necessity to explicitly construct the possible posterior probability distributions". A practical stopping heuristic for the search over measurement points is to take the first reasonable measurement that "on average, splits the candidate space in half". The paper contrasts itself with SOPHIE, which used "an ad hoc half-split method" presupposing a single fault, and notes the cost function could be extended to account for the cost of a test. (Source: [de Kleer and Williams 1987](https://www.fs.isy.liu.se/Edu/Courses/DocDiagnos/CourseMaterial/deKleer_Williams_1987.pdf) `[read]`)
- Later work notes minimum entropy can struggle when the set of diagnoses is very large. (Source: [later model-based diagnosis literature, JAIR](https://jair.org/index.php/jair/article/download/10713/25597/19944) `[excerpt]`)

#### Half-split

- "With every step in the process, the troubleshooter eliminates half the circuit as the cause of the problem. Using this divide-and-conquer philosophy, the first action item might be as simple as asking a question or taking a voltage or resistance measurement with a multimeter." The article's motivating case is a machine where "virtually everything had been changed" over two shifts before half-splitting found a ground fault in a junction box. **[simple]** (Source: [EC&M, The Beauty of Half-Splitting](https://www.ecmweb.com/ops-amp-maintenance/beauty-half-splitting) `[read]`)

### Inferences

A minimal engine that needs no training data, assembled from the cited rules (the assembly is my inference, each ingredient is cited above):

1. **State.** A weight w_s per suspect s (part, joint, net short, "something not in the model"). Normalise to p_s = w_s / sum(w). Start from rough priors by part class and by evidence already in the log, and keep an explicit "other / not modelled" suspect (Breese and Heckerman's "all other" fault).
2. **Tests as rows of a D-matrix.** Each candidate test t has a cost C_t (minutes, plus a risk surcharge as in SACSO) and, for each suspect, the outcome it predicts if that suspect is the fault (fail, pass, or no prediction).
3. **Update after a result.** Hard version (TEAMS style): a passed test clears every suspect that would have made it fail; a failed test restricts suspicion to the suspects that can make it fail. Soft version (preferred, covers measurement error): multiply w_s by a likelihood, for example 0.9 if the outcome matches what s predicts, 0.1 if it contradicts it, 1 if s predicts nothing; then renormalise. The 0.9 and 0.1 play the role of SACSO's P(correct) and of GDE's uncommitted candidates.
4. **Choose the next step.** For a direct check or replacement of suspect s: score = p_s / C_s (Heckerman's ratio). For an information test with pass probability q = sum of p_s over suspects predicting pass (splitting no-prediction mass evenly): gain = -(q*log2(q) + (1-q)*log2(1-q)) bits, score = gain / C_t. This is the binary case of the entropy formulas above. With equal priors and equal costs it reduces to half-split.
5. **Mixing the two scales.** The principled comparison is Breese and Heckerman's: do the observation if ECO < ECR, where ECR is computed by sorting the remaining suspects by p/C. This is a few lines of code for a few dozen suspects. A cruder rule is to prefer information tests while no suspect exceeds some probability (for example 0.5), then switch to p/C checks.
6. **Stop and escalate.** If the "other" suspect dominates, or every remaining test is skipped, say so and fall back to a manual log entry (the "service call").

Further inferences:

- With tens of suspects, not thousands, the NP-completeness of optimal sequencing is irrelevant; greedy one-step choice recomputed after each answer is what every fielded system above does.
- The single-fault assumption is acceptable for ranking but must not be used to delete suspects. Soft updates keep cleared suspects recoverable.
- Costs for a bench repair should include a risk term for powered tests and for desoldering, as SACSO does; otherwise the ranking will propose lifting parts too early.

### Gaps

- The exact statement of Pattipati and Alexandridis's "information gain per unit cost" heuristic was not verified in the 1990 paper (paywalled). The gain/cost rule above is derived from the entropy formulas in Wahl and Sheppard and in de Kleer and Williams, which were read.
- Heckerman, Breese and Rommelse (1995, CACM) itself was not read; its rule is quoted from the 1996 follow-up by two of the same authors.
- The SACSO methodology paper (Jensen et al. 2001) and Ottosen's thesis were inaccessible; SACSO claims rest on Langseth and Jensen 2003, Skaanning 2000 and the HP patent.
- The exact numeric threshold in GDE's stopping heuristic and the closed-form expected-entropy expression were garbled in the OCR copy and are not reproduced.
- No empirical comparison of these rankings on board-level repair with a multimeter was found.

## 4. How can a netlist-level model of a board be used to derive diagnostic steps automatically?

### Takeaway

The literature supplies the mechanism (a dependency or D-matrix computed from connectivity by reachability, and GDE's conflicts computed from which components a contradicted expectation depends on), and repair practice supplies the moves (measure a rail to ground, expand a net through low-ohm series parts, split a net at a series element, compare identical channels). Combining them for a hand-built netlist is an inference: no published tool or paper was found that does this for multimeter-level board repair.

### Cited Findings

- A dependency model can be generated from connectivity: the fault-test matrix "can be computed by the reachability analysis algorithms" from a directed-graph model of the system. (Source: [NASA final report 1997, Pattipati et al.](https://ntrs.nasa.gov/api/citations/19980096374/downloads/19980096374.pdf) `[read]`)
- GDE's inference pattern on a circuit: a prediction depends on a set of components being good; when a measurement contradicts it, that set is a conflict and every diagnosis must include at least one member; measurements that agree with predictions shift probability away from the components involved. It was demonstrated on circuits and needs component behaviour models. (Source: [de Kleer and Williams 1987](https://www.fs.isy.liu.se/Edu/Courses/DocDiagnos/CourseMaterial/deKleer_Williams_1987.pdf) `[read]`)
- Pass and fail propagate to component states: test outcomes of pass, fail or unknown lead to components "good", "bad", "suspect" or "unknown", and suspects with identical test signatures form an ambiguity group that no available test can split. (Sources: [PHM Society paper on D-matrix inference](https://www.papers.phmsociety.org/index.php/phmconf/article/download/2392/1358) `[excerpt]`, [Wahl and Sheppard 2010](https://www.cs.montana.edu/sheppard/pubs/phm-2010.pdf) `[read]`)
- Listing every part on a net is the baseline feature of boardviews: "Clicking on a pin in a part will select the pin and all other parts connected to the same network". FlexBV's Mycelium extends the selection through fuses, inductors, shunts and low-value resistors up to three levels, which treats those parts as electrically joining nets. (Source: [FlexBV manual](https://pldaniels.com/flexbv5/manual/flexbv-manual.html) `[excerpt of fetched page]`)
- Rail-level checks in practice: technicians "checked down the list of power rails" until they found one shorted to ground; in one case, after confirming a short on a standby rail (PP3V42), the inductor was removed to see which side held the fault ("the short was on the system side"). Feeding the rail from a bench supply made the short disappear, attributed to a capacitor on the rail failing open under the applied voltage. (Sources: [Rossmann Group case 1](https://rossmanngroup.com/?p=6010), [Rossmann Group case 2](https://rossmanngroup.com/?p=5571) `[excerpt]`)
- Locating a short along a rail: inject current from a bench supply and probe along the trace with a meter on a low millivolt range to find where the voltage drop stops; on a branched rail, find the shorted branch first. Without removing parts this "is very hard to diagnose ... with just a multimeter" because the differences are a few milliohms. (Source: [All About Circuits forum thread](https://forum.allaboutcircuits.com/threads/diagnosing-short-to-ground-issue.208130/) `[excerpt]`, forum source)
- Diode-mode convention in board repair: red probe on ground, black on the test point, board unpowered; a healthy ground-referenced junction reads roughly 0.7 V and "a reading of 0V would indicate a short circuit". A low reading is not always a fault: "The best check is to compare against an identical channel or a known-good board", and "If in doubt, lift a pin/lead and remeasure". (Sources: [iFixit microsoldering school](https://www.ifixit.com/News/98564/microsoldering-school-day-two-to-fix-the-problem-you-first-have-to-find-the-problem), [Badcaps forum thread](https://www.badcaps.net/forum/troubleshooting-hardware-devices-and-electronics-theory/general-electronics-technical-discussion/82896-testing-for-short-circuit-in-diode-mode), [Siborg guide](https://siborg.com/?p=175) `[excerpt]`)
- Without reference data, compare like with like on the same board: similar pins of one IC, parallel bus lines, and start at connectors, because "faults caused by outside influences can be detected and traced back from the connector to a faulty component". (Source: [Huntron, Fundamentals of Signature Analysis](https://smtnet.com/library/files/upload/ASA%20white%20paper.pdf) `[read]`)

### Inferences

Rules that can be derived mechanically from parts, pins, nets and the per-connection confidence (all are my inferences from the mechanisms cited above, not published rules):

- **Group by rail.** Classify nets as power, ground or signal. For each power rail list its source (regulator, connector pin) and its loads (every part with a pin on it). This is the "list probable faulty functions" step of NEETS made automatic, and the natural first screen: "Rail, expected voltage, parts on it".
- **Suspect set of a symptom.** A symptom attached to a net or part (for example "resets when the motor starts") seeds suspicion on the parts with a pin on the nets involved, then outward through series elements, with weight falling by distance.
- **Rail is not shorted clears shunt shorts.** Measuring resistance or diode drop from a rail to ground, unpowered, tests one hypothesis for every shunt part on the rail at once: "this part is shorted". A healthy reading clears "shorted" for every capacitor, diode and IC supply pin on that rail in one step. It does not clear open or high-ESR capacitors, a dead IC that is not shorted, or an intermittent short, so the engine must track failure modes (short, open, drift, functional) per part, not one flag per part.
- **Rail is shorted spreads suspicion.** A low reading makes every shunt part on the rail a suspect, weighted by class prior (ceramic and tantalum capacitors and semiconductors above resistors), and proposes splitting.
- **Split at a series element.** Find parts with exactly two pins on two different non-ground nets (fuse, ferrite, inductor, 0 ohm link, low-value resistor, jumper, connector). Lifting or opening one divides the suspect set. Choose the split that best halves the suspect probability mass per unit cost (half-split with costs). Desoldering is a costly, risky test and should score accordingly.
- **Failed test raises connected parts.** A powered voltage that is wrong on a net forms a conflict over {source of the net, series path to the test point, every load that could drag it down}. Intersecting conflicts from several measurements narrows candidates exactly as in GDE, without needing full behaviour models, as long as each test declares which parts it depends on.
- **Passed continuity confirms the model, not just the board.** A continuity test between two pins the model says share a net is also evidence for the connection, and can promote its confidence to `measured`. A failed one is ambiguous between "open on the board" and "model wrong", and the tool should say so.
- **Use confidence as test reliability.** A test whose reasoning passes through an `assumed` or `photo` connection should have its likelihood ratio flattened towards 1 (the result means less), and the tool can propose verifying that connection first when it gates many conclusions. A net is only as certain as its weakest link.
- **Unknown pins limit clearing.** Pins not on any net are unknown, so "every part on the rail" is a lower bound. A cleared rail does not clear parts whose supply pin is unmapped; the tool should list them as "not covered".
- **Ambiguity groups are honest end states.** Parts in parallel between the same two nets cannot be separated by in-circuit meter tests. The tool should present them as a group and offer the only splitting tests left (lift one leg, thermal check under injection, replace the cheapest).
- **Same-board comparison generates expectations.** Identical parts wired the same way (two motor driver channels, several decoupling capacitors, parallel LEDs) should read alike; the netlist can find these symmetric groups and propose compare-and-flag-the-odd-one tests, which need no reference data.

### Gaps

- No paper or tool was found that derives multimeter test steps from a reverse-engineered netlist. The rules above are a synthesis and need validating on the example board.
- No sourced failure-rate priors by component class for consumer boards were found in this research; the class ordering above is conventional bench wisdom and unsourced.
- Short-location sources are forums and repair blogs, not controlled studies. Safe injection limits (voltage at or below the rail's nominal value, current limit) were not sourced and must be before any injection step is offered to a novice.
- Model-based diagnosis of analog behaviour (what voltage to expect at an arbitrary node) needs component models the app does not have. Only topology-level reasoning is supported by what was found.

## 5. What design lessons exist for procedures followed by novices?

### Takeaway

The guidance from aviation checklists, nuclear procedure writing, repair-guide style guides and wizard UX converges: one imperative action per step with the object named exactly as on the equipment, the expected value stated in the step, hazards stated immediately before the step they apply to, conditions written before actions, the response recorded as the actual value and not just "checked", visible place-keeping, and a way to decline a step. Novices need a read-do procedure; experts need a faster path through the same content.

### Cited Findings

#### Checklists

- Two methods exist. In "challenge-response" the checklist "is a backup": the crew configures from memory, then verifies. In the "do-list" ("call-do-response") "the checklist is used to 'lead' and direct the pilot in configuring the aircraft using a step-by-step, 'cook book' approach". Do-lists "are generally very detailed and time-consuming", and without the redundancy of a prior configuration "a mistake can easily pass unnoticed once the sequence is interrupted". (Source: [Degani and Wiener 1990, Human Factors of Flight-Deck Checklists: The Normal Checklist, NASA CR 177549](https://ntrs.nasa.gov/api/citations/19910017830/downloads/19910017830.pdf) `[read]`)
- Guideline 4: "Checklist responses should portray the desired status or the value of the item being considered (not just 'checked' or 'set')." (Source: [Degani and Wiener 1990, Appendix A](https://ntrs.nasa.gov/api/citations/19910017830/downloads/19910017830.pdf) `[read]`)
- Guideline 5: "The use of hands and fingers to touch appropriate controls, switches, and displays while conducting the checklist is recommended." Guideline 6: the completion call "should be written as the last item on the checklist". (Source: [Degani and Wiener 1990, Appendix A](https://ntrs.nasa.gov/api/citations/19910017830/downloads/19910017830.pdf) `[read]`)
- Guideline 7: "A long checklist should be subdivided to smaller task-checklists or chunks that can be associated with systems and functions." Guideline 8: sequencing "should follow the 'geographical' organization of the items ... and be performed in a logical flow". (Source: [Degani and Wiener 1990, Appendix A](https://ntrs.nasa.gov/api/citations/19910017830/downloads/19910017830.pdf) `[read]`)
- Guideline 10: "The most critical items on the task-checklist should be listed as close as possible to the beginning ... in order to increase the likelihood of completing the task before interruptions may occur", and this takes precedence over geographical order. Guideline 11: critical items that might be reset "should be duplicated between task-checklists". Guideline 12: checklists should not be tightly coupled with other tasks, with "buffers for recovery from failure". Guideline 14: checklist use "is highly susceptible to production pressures". (Source: [Degani and Wiener 1990, Appendix A](https://ntrs.nasa.gov/api/citations/19910017830/downloads/19910017830.pdf) `[read]`)
- Gawande's formulation: a DO-CONFIRM checklist is run after the team has performed tasks from memory, at a pause; with READ-DO, people "carry out the tasks as they check them off"; and a checklist needs a clear "pause point" at which it is used. "A Checklist for Checklists" was produced by Gawande, the Brigham and Women's Center for Surgery and Public Health and Boeing's Dan Boorman. (Sources: [Project Check, checklist for checklists page](https://www.projectcheck.org/checklist-for-checklists.html) `[read]` for authorship only, [quotation from The Checklist Manifesto](https://www.goodreads.com/quotes/7810944-you-must-decide-whether-you-want-a-do-confirm-checklist-or), [summary of the book's guidance](https://www.projectmanagement.com/blog-post/21259/creating-a-killer-checklist--lessons-from--the-checklist-manifesto-) `[excerpt]`)

#### Procedure and work-instruction writing

- Write action steps as commands: "Imperative sentences (commands) are used", not "shall" statements, and "Start the basic action step with a singular present tense action verb". Identify equipment "precisely as it is in the facility". Use words "easily understandable by the users"; a definition goes in the step or "as a note that immediately precedes the action step". Avoid sub-substeps, and put three or more objects of one verb in a table "with appropriate checkoff boxes". (Source: [DOE-STD-1029-92, Writer's Guide for Technical Procedures](https://www.osti.gov/servlets/purl/308015) `[read]`)
- Level of detail: "Write procedures to a level of detail consistent with the qualifications and training" of the users; detail can drop as qualification and task frequency rise and should rise with complexity. (Source: [DOE-STD-1029-92, section 3.1.1](https://www.osti.gov/servlets/purl/308015) `[read]`)
- Conditional steps use only IF or WHEN, THEN, AND, OR, NOT; words such as "except", "unless", "but", "only" "should never be used to present conditional information", and one must "Describe the condition first and then the action". Conditional terms are emphasised and each starts on a new line. (Source: [DOE-STD-1029-92, section 4.2](https://www.osti.gov/servlets/purl/308015) `[read]`)
- Warnings and cautions: "Position warnings and cautions so they are complete on one page and appear immediately before and on the same page as the action step(s) to which they apply." "Do not include action steps in warnings and cautions." Write them "as statements rather than as commands", giving the hazard, "the consequences of failing to heed" it and any time limits; one topic each; do not use all capitals; hazards present throughout go in a precautions section and are repeated at the steps they apply to; and "Avoid overusing warnings and cautions". The guide cites an industry study attributing "one-fourth of all human performance events to a failure to provide proper warnings and cautions". (Source: [DOE-STD-1029-92, section 4.10.1](https://www.osti.gov/servlets/purl/308015) `[read]`)
- Acceptance criteria "provide a basis for determining the success or failure of an activity" and "may be qualitative ... or quantitative (specify a value or value range)", stated at the step where the check is done, with "actions to be taken immediately by the user, in the event that specified acceptance criteria are not met". Example of value plus range in a step: "Verify that each cylinder regulator will maintain 35 psig (30 to 40 psig)". (Source: [DOE-STD-1029-92, sections 4.1 and 4.12](https://www.osti.gov/servlets/purl/308015) `[read]`)
- Data and place-keeping: "Provide appropriate space or tables for entering data"; "Placekeeping helps users to keep track of their progress in a procedure and reduces the probability of omitting or duplicating action steps", with a check-off box near each step when signatures are not needed. (Source: [DOE-STD-1029-92, sections 4.9 and 4.13](https://www.osti.gov/servlets/purl/308015) `[read]`)
- Status of that guide: DOE-STD-1029-92 was cancelled in 2015 in favour of industry procedure-writing standards (PPA AP-907-005); it remains a freely readable statement of the same practices. (Source: [DOE standards page](https://www.standards.doe.gov/standards-documents/1000/1029-astd-1992-cn1-1998) `[excerpt]`)
- iFixit's guidance for guide text: write for readers with little technical knowledge, use the active voice, say what to do and how ("use an iFixit opening tool to pry the battery out", not "Remove the battery"), name tools and components correctly, give counts and sizes ("four 5.5 mm Phillips #00 screws"), and leave out obvious or repetitive steps. (Source: [iFixit EDU, Write guide text](https://edu.ifixit.com/standard-project/write-guide-text) `[excerpt of fetched page]`)
- iFixit's Tech Writing Handbook: organise by task, "arrange things in the order they need to be done", include prerequisite tasks as steps, let "visuals do most of the talking", state difficulty, a realistic time estimate (add 20 to 50 percent to an expert's time for novices) and the tools up front, and collect feedback because "great instructions don't happen on the first try". (Source: [iFixit Tech Writing Handbook, chapter 8](https://about.ifixit.com/Tech_Writing/chapter/8) `[excerpt of fetched page]`)
- iFixit's style, as reported: each bullet is one idea or action, the action is the first bullet of a step, each step has at least one photo, and a warning may precede an action when needed though iFixit prefers it after when possible. This last point conflicts with the DOE rule above. (Sources: [iFixit EDU editing guidance](https://edu.ifixit.com/edit-edit-edit), [third-party analysis of iFixit guides](https://jesse-schooff-hhct.squarespace.com/single-post/2019/4/18/your-instructions-are-bad-but-dont-feel-bad) `[excerpt]`; contradicted on warning placement by [DOE-STD-1029-92](https://www.osti.gov/servlets/purl/308015))
- The RetroTech wiki house style: instructions as commands, exact values and part numbers, and "State hazards plainly ... Then let the reader decide". (Source: [RetroTechCollection, Writing a repair guide](https://retrotechwiki.com/Help:Writing_a_repair_guide) `[read]`)

#### Wizards and guided workflows

- A wizard suits "novice users or people who have little domain knowledge" and infrequent processes, and is wrong for experts or frequent tasks, who need a faster alternative. Costs: comparing information across steps is hard, interruption can lose work, and a modal wizard blocks the rest of the app the user may need. (Source: [Nielsen Norman Group, Wizards](https://www.nngroup.com/articles/wizards/) `[excerpt of fetched page]`)
- Recommendations: show the list of steps and the current position, label buttons with what the next step is and include Back, allow saving and resuming, make each step self-sufficient (show needed data inside the step), and put explanations in a side panel beside the step, not over it. (Source: [Nielsen Norman Group, Wizards](https://www.nngroup.com/articles/wizards/) `[excerpt of fetched page]`)

#### Skipping, "can't do it", expert override and the reason for a step

- In the HP troubleshooter the user may decline a suggested step "if he is unable to perform it, or simply doesn't want to at the moment"; the step is deferred and re-offered only when untried steps run out. The cost model includes "insult", the cost of proposing a step too basic for the user, and on failure the full log and final cause probabilities pass to a human expert who "will be able to save much time by skipping steps already performed". (Sources: [US patent 6,535,865](https://patents.google.com/patent/US6535865) `[excerpt of fetched page]`, [Skaanning 2000](https://arxiv.org/pdf/1301.3893) `[read]`)
- GDE treats a hypothesis that predicts nothing for a measurement as uncommitted, spreading its probability evenly over outcomes, which is the formal model for "this answer tells us nothing about that suspect". (Source: [de Kleer and Williams 1987](https://www.fs.isy.liu.se/Edu/Courses/DocDiagnos/CourseMaterial/deKleer_Williams_1987.pdf) `[read]`)
- Boeing's FIM leaves judgement to the technician ("Use your judgement to decide which corrective action to do first") while requiring repair confirmation after any action, including one outside the task. (Source: [AviationHunt](https://aviationhunt.com/?p=6844) `[excerpt of fetched page]`)
- Decision-tree products provide Back, Restart and a "View my responses" list of answers given, each usable to return to that node. (Sources: [Zingtree help](https://help.zingtree.com/hc/en-us/articles/5003243194651), [ServiceNow decision tree docs](https://www.servicenow.com/docs/r/5M2H7PAkXUuakbtz~5Kfeg/GtEU3GitckLHvuEVyncsNg) `[excerpt]`)
- Empirical research on troubleshooting: skilled electronics technicians' procedures look inefficient "from an information-economy view" but are rational for minimising time and mental load, and when they fail they tend to repeat routines. A review of troubleshooting training found the effect of instruction "is highly related to the level of explicitness of action-related information provided". (Sources: [Rasmussen and Jensen 1974 record](https://orbit.dtu.dk/en/publications/mental-procedures-in-real-life-tasks-a-case-of-electronic-trouble/), [Morris and Rouse 1985 record](https://scilit.net/publications/800ecdc196e4999e2083a21bddf0d214) `[excerpt]`, abstracts only)

### Inferences

A step template that satisfies the cited rules:

- **Preconditions**, as state the technician confirms: power off or on, adapter unplugged, meter mode and range, which probe goes where.
- **Hazard statement** (only if one applies), placed before the action, phrased as a statement with its consequence.
- **One action**, imperative, naming the part and pin exactly as the board view shows it, with the board photo highlighting both probe points (the software equivalent of "touch the control").
- **Expected result with a range and unit**, and where the expectation comes from (physics, datasheet, same-board comparison, or none).
- **Response**: the measured value itself, plus explicit non-answers: "could not measure", "reading unstable", "not sure", "skip for now".
- **Why this step**: one line naming the suspects it separates ("clears C3, C7, U4 as shorted if above 100 ohm"), kept beside the step.
- **Outcome**: what the tool concluded and how the suspect list changed, with undo.

Further inferences:

- The tool is a do-list (read-do) for the novice. Degani and Wiener's warning that an interrupted do-list hides errors means the session must persist its exact place and the board state it assumes (powered or not, parts lifted), and restate that state on resume.
- "Most critical first" translates to: safety and "do no harm" checks (rail shorts before applying power, adapter voltage before connecting) come before the information-optimal test, as hard ordering constraints on the ranking, not as costs.
- Chunking by function (power input, each rail, motor driver, logic) gives short task-lists with a visible end, and matches the rail grouping of section 4.
- An expert path costs little: show the ranked candidate tests and let the user pick any, enter a result for a test the tool did not ask for, or assert a conclusion with a note. All go through the same update and log.
- The warning-placement conflict (DOE before, iFixit after when possible) should be resolved in favour of before for anything that can damage the board or the person, since the novice acts on the first thing read.
- Non-answers must leave the probabilities unchanged and mark the test as deferred, never be coerced into pass or fail.

### Gaps

- The full item list of "A Checklist for Checklists" (including any numeric limit on items) could not be retrieved; the "five to nine items" figure often quoted from Gawande is unverified here.
- FAA checklist design guidance other than the NASA report was not retrieved. Degani and Wiener's guidelines are for normal flight-deck checklists, so their transfer to bench diagnosis is by analogy.
- No vendor documentation for electronic work-instruction software (Tulip, VKS, Dozuki product features) was read, only iFixit's writing guidance.
- No usability study of decision-tree or wizard-style troubleshooting with novices at a bench was found; Rasmussen and Jensen, and Morris and Rouse, were seen only as abstracts.
- No source was found on how best to word "why this step is asked" for technicians.

## 6. What should be recorded so the diagnosis is reproducible?

### Takeaway

Record raw observations with their conditions separately from interpretations, keep hypotheses as first-class items with a status and links to the observations that moved them, and close the loop with a verification after the fix. The formal standards (FRACAS, 8D, IPC-7711/7721) are organisational, but their skeleton, namely report, verify the failure, analyse, correct, verify the correction, close out, scales down to one board.

### Cited Findings

- NEETS step 6 includes, as part of the repair itself, to "determine what caused the failure, return the equipment to its proper operating status, and record the necessary information in a recordkeeping book for other maintenance personnel in the future". (Source: [NEETS Module 19](https://electriciantraining.tpub.com/14191/css/Classes-Of-Overhaul-Work-145.htm) `[read]`)
- MIL-HDBK-2155 (1995, superseding MIL-STD-2155 of 1985) structures FRACAS as failure reporting, failure analysis, failure verification, corrective action, failure report close-out, and identification and control of failed items. Practice guidance adds that the loop closes only after monitoring confirms the failure has not recurred. (Sources: [EverySpec listing of MIL-HDBK-2155](https://everyspec.com/MIL-HDBK/MIL-HDBK-2000-2999/MIL-HDBK-2155_21714/), [Wikipedia, FRACAS](https://en.wikipedia.org/wiki/Failure_reporting,_analysis,_and_corrective_action_system), [Tractian glossary](https://tractian.com/en/glossary/fracas-failure-reporting-analysis-corrective-action-system) `[excerpt]`)
- A FRACAS should capture incident reports, failure mode and severity, the analysis method and results "used to determine the root cause", and corrective actions "verified after implementation". (Source: [PTC Windchill, What information should a FRACAS capture](https://support.ptc.com/help/wrr/r13.0.2.0/en/wrr/ReferenceGuide/fracas/what_info_should_fracas_capture.html) `[excerpt of fetched page]`)
- 8D runs from D0 (plan, record the symptoms and any emergency response) through D2 (describe the problem), D3 (interim containment), D4 (root cause), D5 (choose and verify the permanent correction), D6 (implement and validate), D7 (prevent recurrence) to D8 (close and recognise the team). D1 and D8 are team steps. (Sources: [ASQ, Eight Disciplines](https://asq.org/quality-resources/eight-disciplines-8d), [Wikipedia, Eight disciplines problem solving](https://en.wikipedia.com/wiki/Eight_disciplines_problem_solving) `[excerpt]`)
- IPC-7711/7721 "prescribes the procedural requirements, tools, materials and methods" for rework, repair and modification of electronic assemblies, applies when invoked by contract, does not limit the number of repair actions on an assembly, and allows alternate equipment if the user establishes the result is undamaged. Revision D is the current one (dated 2023 or 2024 depending on the listing). It governs how a repair is executed, not how a fault is diagnosed. (Sources: [ANSI webstore, IPC-7711/7721D](https://webstore.ansi.org/standards/ipc/ipc77117721d2024), [IPC-7711/7721C preview](https://webstore.ansi.org/preview-pages/IPC/preview_IPC+7711+7721C-2017.pdf) `[excerpt]`)
- Laboratory notebook practice: keep the data section free of analysis and draw conclusions afterwards; record observations soon after they are made; include all raw data; "Label clearly! Use unit labels!"; do not erase raw data; and write so that "someone from outside your lab" can follow what was done without verbal explanation, including set-up details and methods. (Sources: [University of Texas notebook guide](https://sites.utexas.edu/membraneresearch/files/2012/07/LabNotebookKeeping.pdf), [Hobart and William Smith notebook style guide](https://people.hws.edu/craig/chem348/notebook.htm), [University of Kentucky good practices](https://medicine.uky.edu/news/good-practices-laboratory-notebooks-2013-07-23t12-57-53), [Penn State data management unit](https://sites.psu.edu/ethicsofdatamanagement/unit-2-generating-data/2-3-lab-notebook) `[excerpt]`)
- Responses should carry the value, "not just 'checked' or 'set'". (Source: [Degani and Wiener 1990, guideline 4](https://ntrs.nasa.gov/api/citations/19910017830/downloads/19910017830.pdf) `[read]`)
- Measurement conditions change the meaning of a reading: the repair convention for diode mode is red probe on ground with the board unpowered, analog signatures depend on the voltage, source resistance and frequency used so "reference and test" must match, and an in-circuit reading may need a lifted pin to be conclusive. (Sources: [Badcaps forum thread](https://www.badcaps.net/forum/troubleshooting-hardware-devices-and-electronics-theory/general-electronics-technical-discussion/82896-testing-for-short-circuit-in-diode-mode), [Metromatics on Huntron settings](https://metromatics.com.au/product/analog-signature-analysis-huntron-tracker/) `[excerpt]`)
- Existing tools record three kinds of trace: reference readings per net as diode, voltage and resistance (FlexBV and OpenBoardData), a per-session "diagnosis protocol" (VW ODIS), and the log of suggested and performed steps with final cause probabilities handed to the next person (HP). Wrench Board sessions can be replayed. (Sources: [FlexBV manual](https://pldaniels.com/flexbv5/manual/flexbv-manual.html), [ODIS manual copy](https://www.scribd.com/document/493942193/ODIS-Service-Manual), [US patent 6,535,865](https://patents.google.com/patent/US6535865), [Fight to Repair](https://fighttorepair.substack.com/p/how-ai-is-set-to-transform-electronics) `[excerpt]`)
- Symptom disappearance is not proof of repair for intermittent faults; stability should be confirmed over repeated cycles. (Source: [troubleshooting study guide](https://www.remnote.com/learn/engineering/core-engineering/electrical-engineering/troubleshooting/troubleshooting-study-guide) `[excerpt]`, a low-authority secondary source)

### Inferences

A record model sized for one board (my synthesis of the above):

- **Session**: symptom as first observed, symptom elaboration (when, how often, what else is wrong), initial evaluation result ("fault reproduced: yes, no, intermittent"), start time.
- **Observation** (immutable once saved; corrections are new entries that supersede): timestamp; step it answers, if any; quantity (voltage, resistance, diode drop, continuity, visual, thermal, behaviour); value and unit; probe points (positive on pin, negative on pin or ground); meter mode and range; board state (unpowered or powered, supply voltage, which load or mode is active); in circuit or lifted, with which leg; stability (steady, drifting, intermittent); instrument; photo if any; free note. A non-answer is also an observation ("could not reach pin", "skipped").
- **Expectation**: value or range, and its basis (physics of the netlist, datasheet, same-board comparison, external reference). The basis is what lets a later reader judge the conclusion.
- **Inference**: produced by the tool or the user, linking one or more observations to a change in one or more hypotheses, with the rule applied ("rail not shorted clears shunt shorts on +5V"). Kept separate from observations so it can be recomputed or retracted when the netlist or an expectation changes.
- **Hypothesis** (suspect): subject (part, joint, net, or "not in model"), failure mode, status (open, suspected, cleared, confirmed, repaired), current weight, and the list of supporting and contradicting observations.
- **Action**: any change to the board (part lifted, replaced, reflowed, wire added), with before and after photos, because actions invalidate earlier observations on the nets they touch.
- **Closure**: fix applied, repair confirmation test and how many cycles it passed, probable root cause (why the part failed), and what would be checked first next time.

Further inferences:

- The app's existing confidence ladder for connections (`measured` to `assumed`) is the same idea applied to the model; using one vocabulary for "how do we know" across connections, expectations and conclusions keeps the log readable.
- Because scores are recomputable from the observation list, storing observations and rules, not just the current suspect ranking, gives undo, audit and "what if this reading was wrong" for free.
- FRACAS and 8D items that do not scale down: team formation, containment across a product population, recurrence prevention across a fleet. Items that do: verify the failure before analysis, verify the correction, record root cause, close out explicitly.

### Gaps

- MIL-HDBK-2155's actual data element list was not read (the handbook text was not retrieved), so no field-level mapping to FRACAS is claimed.
- No standard was found that prescribes how to record a bench measurement for repair (probe polarity, power state, in or out of circuit). The field list above is assembled from practice sources.
- IPC-A-610 and any IPC requirement on repair records were not researched beyond the scope statement of IPC-7711/7721.
- The lab-notebook sources are university teaching guides, not a standard.

## 7. What are the known pitfalls of rigid decision trees for troubleshooting, and how do good tools mitigate them?

### Takeaway

Static trees fail in predictable ways: they encode one order and one fault, grow unmanageably, go stale, dead-end when the case is not in the tree, and treat every answer as certain. The mitigations seen in fielded tools are to recompute the next step from a cause model, keep an explicit "none of the modelled causes" outcome with a hand-off, verify the fault before and after, treat answers as fallible evidence, and let the technician defer or reorder steps.

### Cited Findings

- Static and costly to build: every allowed sequence must be encoded by hand, the tree grows exponentially, and the result is "longer troubleshooting sequences with lower probability of actually diagnosing the problem". (Source: [US patent 6,535,865](https://patents.google.com/patent/US6535865) `[excerpt of fetched page]`)
- Hard to maintain: "modeling decision trees becomes quickly cumbersome and maintaining them very complex and error prone, especially for unexperienced users"; hand-built flowcharts drift toward sub-optimal over time; static flowcharts give authors no feedback on whether they solve problems. (Sources: [Scitepress paper on Bayesian troubleshooting models](https://www.scitepress.org/Papers/2010/29777/29777.pdf), [US patent 8,341,610](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/8341610), [US patent 10,108,440](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/10108440) `[excerpt]`)
- Missing and wrong branches in a deployed OEM system: fault codes with "no test created in current test plans", a test step that reports a voltage "is OK" when the starter did not turn, and a step naming a different module from the wiring diagram. (Source: [VW ODIS bulletin via NHTSA](https://static.nhtsa.gov/odi/tsbs/2022/MC-10209102-0001.pdf) `[read]`)
- Wrong path chosen: more branches make it likelier the user picks the wrong one, and trees cannot handle multi-layered problems that need trial and error. (Source: [Mavenoid blog](https://www.mavenoid.com/en/blog/diagnostic-vs-decision-tree-approach-which-is-better-for-support) `[excerpt of fetched page]`, vendor marketing)
- Single-fault assumption: fault trees "are limited to a single-fault assumption and become unreliable with multiple faults"; half-split as used in SOPHIE presupposed "that the circuit contains a single fault"; the decision-theoretic ranking is exact only for a single fault and runs "albeit approximately" otherwise. (Sources: [DTIC ADA455068](https://apps.dtic.mil/sti/tr/pdf/ADA455068.pdf) `[excerpt]`, [de Kleer and Williams 1987](https://www.fs.isy.liu.se/Edu/Courses/DocDiagnos/CourseMaterial/deKleer_Williams_1987.pdf) `[read]`, [Breese and Heckerman 1996](https://arxiv.org/pdf/1302.3563) `[read]`)
- Multiple faults in practice: with several faults there are "hidden faults" and "masking false failures"; the remedy is a test-and-repair cycle that removes the repaired item from the suspect group and runs the strategy again. GDE handles multiple faults natively through conflicts and minimal candidates. (Sources: [NASA final report 1997](https://ntrs.nasa.gov/api/citations/19980096374/downloads/19980096374.pdf) `[read]`, [de Kleer and Williams 1987](https://www.fs.isy.liu.se/Edu/Courses/DocDiagnos/CourseMaterial/deKleer_Williams_1987.pdf) `[read]`)
- Intermittent faults: they are "regarded as the most difficult class of faults to diagnose" and a main root cause of No Fault Found; one cited electronics study attributes 80% of intermittent faults to loose or contaminated interconnections; time pressure is among the major NFF causes. (Sources: [Cranfield NFF review, part 2](https://dspace.lib.cranfield.ac.uk/handle/1826/9948), [Cranfield intermittent fault study](https://dspace.lib.cranfield.ac.uk/items/8bb30a01-23c3-4510-9b46-3b86a2915182/full), [Khan et al. review copy](https://core.ac.uk/download/228143862.pdf) `[excerpt]`)
- Handling intermittents formally: de Kleer's extension gives each component a prior of being intermittently faulty and a probability g(c) that a faulty component "is behaving correctly" on a given observation, so a good reading only reduces suspicion and does not clear it. Example figures in the patent: 10^-5 chance a roller is worn, 0.01 chance a worn roller malfunctions on a given sheet. (Sources: [de Kleer 2009, IJCAI](https://ijcai.org/proceedings/2009/127), [US patent 8,024,610](https://patents.google.com/patent/US8024610) `[excerpt]`)
- Handling intermittents procedurally: the FIM's Initial Evaluation verifies the fault exists before isolation, declares an intermittent when it cannot be reproduced, and sends the technician to a separate inspection for wiring. (Source: [AviationHunt](https://aviationhunt.com/?p=6844) `[excerpt of fetched page]`)
- Technician and test error: a failed test may be a false alarm; SACSO multiplies each step's effect by P(done correctly), its "inaccuracy factor"; Huntron and repair forums advise confirming an odd reading by comparison with an identical channel or by lifting a pin. (Sources: [NASA TEAMS-RT paper](https://ntrs.nasa.gov/api/citations/20140008893/downloads/20140008893.pdf) `[excerpt]`, [Skaanning 2000](https://arxiv.org/pdf/1301.3893) `[read]`, [Huntron white paper](https://smtnet.com/library/files/upload/ASA%20white%20paper.pdf) `[read]`)
- Wrong priors and fixation: technicians who fail tend to repeat routines; the EC&M case had "virtually everything" replaced before anyone measured; NEETS warns to "Analyze the cause of the failure for a possible underlying problem". (Sources: [Rasmussen and Jensen 1974 record](https://orbit.dtu.dk/en/publications/mental-procedures-in-real-life-tasks-a-case-of-electronic-trouble/) `[excerpt]`, [EC&M](https://www.ecmweb.com/ops-amp-maintenance/beauty-half-splitting) `[read]`, [NEETS Module 19](https://electriciantraining.tpub.com/14191/css/Classes-Of-Overhaul-Work-145.htm) `[read]`)
- Dead ends: iFixit reserves a conclusion for "next steps if nothing among the causes and solutions has worked"; Breese and Heckerman add an "all other" fault repaired by a service call; the HP system hands the log and probabilities to a human; VW tells technicians to send test-plan feedback and use the repair manual. (Sources: [iFixit Problem Page](https://www.ifixit.com/Info/Problem_Page), [Breese and Heckerman 1996](https://arxiv.org/pdf/1302.3563) `[read]`, [US patent 6,535,865](https://patents.google.com/patent/US6535865), [VW bulletin](https://static.nhtsa.gov/odi/tsbs/2017/MC-10133469-9999.pdf) `[excerpt]`)
- Limits of the dynamic alternatives: the greedy efficiency rule is not guaranteed optimal; pure dependency inference leaves large suspect sets; minimum entropy struggles with very many candidates; Bayesian troubleshooters need an expert to elicit causes, probabilities and costs (HP built an authoring tool for exactly this bottleneck). (Sources: [Langseth and Jensen 2003](https://www.fs.isy.liu.se/Edu/Courses/DocDiagnos/CourseMaterial/troubleshooting_coherent_systems.pdf) `[read]`, [US patent 5,544,308](https://patents.google.com/patent/US5544308) `[excerpt]`, [Skaanning 2000](https://arxiv.org/pdf/1301.3893) `[read]`)

### Inferences

Pitfall-to-mitigation map for the Investigate feature (synthesis):

| Pitfall                                  | Mitigation supported by the sources                                                                                                                                                              |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Fixed order, cannot skip                 | Rank candidate steps from the current state after every answer; allow defer and "pick another"; re-offer deferred steps last (HP)                                                                |
| Dead end, cause not in the tree          | Always carry an "other / not in the model" suspect; when it dominates or tests run out, say so, summarise what was cleared, and switch to free-form logging (Heckerman's service call)           |
| Wrong priors                             | Use weak priors; let evidence dominate; show the ranking and let the user override a weight with a note; never display a probability as a certainty                                              |
| Multiple faults                          | Never hard-delete suspects; after a fix, re-run the confirmation and, if the symptom remains, continue with the repaired part removed from the suspect group (Pattipati's test-and-repair cycle) |
| Intermittent fault                       | Start with "is the fault present now"; a passing test on an intermittent only lowers a weight (de Kleer's g); record stability of each reading; require several cycles before closing            |
| Measurement error by a novice            | Soft likelihoods instead of hard elimination; ask for a repeat or a cross-check when a single reading would clear or convict a strong suspect; highlight probe points on the photo               |
| Model error (netlist wrong)              | Weaken conclusions that pass through low-confidence connections; offer "verify this connection" as a test; treat a surprising reading as possible model error as well as a possible fault        |
| Step is wrong, unsafe or impossible here | Per-step "cannot do, does not apply, looks wrong" exits that are logged and do not change scores (the VW defects show authored steps will be wrong sometimes)                                    |
| Stale content                            | Generate steps from the scenario model at run time, so edits to parts, nets and confidence change the plan at once                                                                               |
| Fixation on one suspect                  | Show how much each proposed test would change the picture; show what remains unexplained                                                                                                         |

- A hybrid is the pragmatic design: a short authored opening (symptom elaboration, safety, power-input checks) followed by a model-driven loop. The authored part carries expert knowledge the netlist cannot (known weak parts such as U4 on the example board); the loop prevents dead ends.
- Because the sources agree that no ranking is optimal under real conditions, the interface should present the next step as a recommendation with a visible reason, and never hide the alternatives.

### Gaps

- No quantitative comparison of static trees against dynamic troubleshooters in electronics repair was found. The only figure seen (a "four times" resolution-rate claim) is vendor marketing and is not reported as fact.
- NFF rates were not retrieved; the 80% interconnection figure is a secondary citation inside a Cranfield paper.
- No study was found of how often novice technicians misreport multimeter readings, so the suggested soft likelihood values (such as 0.9 and 0.1) are placeholders, not evidence.
- The fixation and "repeat routine" findings come from abstracts of 1970s and 1980s studies of trained technicians, not novices with software guidance.
